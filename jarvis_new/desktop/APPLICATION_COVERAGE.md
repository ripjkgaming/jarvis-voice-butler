# STARK OS application coverage

Application assets are generated by `build_app_extras.py` using the canonical
palette from `build.py` and `design/STARK_OS.md`. This generator never applies
settings. Its outputs live in `app-extras/`; the main desktop installer handles
backups and installation. Re-run in isolation with:

```sh
python3 desktop/build_app_extras.py --output /tmp/stark-app-assets
/usr/bin/python3 desktop/verify_app_extras.py --assets /tmp/stark-app-assets
```

## Observed starting state, 1 October 2026

The live KDE configuration selected `StarkOS` colors, Rajdhani 11pt general UI,
and Share Tech Mono 10pt fixed text. It had no explicit `widgetStyle` key.
GTK 3 and GTK 4 selected `Adwaita`, an incorrect `Rajdhani, Black 11` font string,
`jarvis-command` icons and `Nordic-cursors`. The small existing icon overlay
contained only three reactor launcher icons. The generated Konsole baseline
selected JetBrainsMono Nerd Font 11pt. These were gaps between the desktop and
the canonical HUD spec.

## Coverage and integration

| Surface | Implementation and application | Limits |
|---|---|---|
| KDE/Qt Widgets | Explicit Breeze widget style with the existing `StarkOS` KDE color scheme and canonical font settings; native menus, dialogs, file choosers, toolbars and controls use the palette. | Application stylesheets, hardcoded colors and custom drawing can override the palette. Breeze retains native geometry, so controls are not exact copies of HUD chamfers. |
| GTK 3 | Install `themes/StarkOS` under XDG data `themes/`; select `gtk-theme-name=StarkOS`, `gtk-font-name=Rajdhani Medium 11` in `gtk-3.0/settings.ini`. GTK CSS covers client title bars, menus, popovers, forms, tabs, lists, selection, scales, checkboxes, tooltips, focus and scrollbars. | Existing app windows may require normal reopening. App CSS and bundled theme providers can override this. |
| GTK 4, ordinary apps | Same named theme and settings in `gtk-4.0/settings.ini`; imports toolkit Default dark widget geometry, then applies STARK tokens. | Applies to GTK applications that honor the named theme, not every GTK 4 app. No global `gtk-4.0/gtk.css` injection is used. |
| GTK 2 | Engine-free `gtk-2.0/gtkrc`, canonical state colors and font. The installer updates the effective user-writable `GTK2_RC_FILES` path (here `~/.gtkrc-2.0-kde4`) as well as the managed fallback block in `~/.gtkrc-2.0`. Old theme includes in the effective file are replaced while unrelated options remain. | Legacy native engine geometry is retained. Application-specific RC rules may take priority. GTK2 does not implement GTK3 CSS. System-owned or other-user RC files are never edited. |
| GTK transport settings | `gtk_integration.py` synchronizes the theme through KDE's supported `setGtkTheme` method, sets owned GSettings appearance keys, and updates theme/font/icon/cursor keys in XSettings. An existing same-user xsettingsd receives SIGHUP to reload. | No preview or new daemon is launched. GSettings/desktop notifications need the normal session bus; sandbox verification uses the native keyfile backend instead. |
| Old user CSS overrides | Remove the exact earlier `/* Jarvis theme begin */` block from GTK3/4 user CSS. Keep other CSS and KDE's `colors.css` import. | Unrecognized user edits are preserved. No new global CSS override is injected into libadwaita. |
| Icons | `icons/stark-os`: generated SVG icon theme covering the reactor launcher, folders, home/trash, terminal, file manager, settings, documents, common actions and semantic status. Select KDE `Icons/Theme=stark-os` and GTK `gtk-icon-theme-name=stark-os`. The verifier discovers the complete generated SVG inventory dynamically. | Inherits installed `breeze-dark,breeze,hicolor` for complete coverage. Third-party brands, embedded app icons, custom tray pixmaps and uncovered glyphs keep their identity. Never claim every icon was redrawn. |
| Cursors | `icons/stark-os-cursors`: high contrast default arrow, text, crosshair, wait and progress shapes, aliases and Breeze fallback. Each file embeds 24/32/48/64px images. Select `kcminputrc/Mouse/cursorTheme=stark-os-cursors` and GTK `gtk-cursor-theme-name=stark-os-cursors`; existing cursor size preferences are preserved (GTK was 24 during the audit). | Specialized resize/hand/drag cursors inherit Breeze; application/client cursor surfaces may ignore the system theme. Existing processes may cache cursors until their normal restart. No compositor restart is needed. |
| Konsole | The main `konsole/StarkOS.profile`, generated by `build.py`: Share Tech Mono 10pt, cyan cursor and 10px margins. `StarkOS.profile` remains the selected default; no duplicate Canonical profile is needed. | Existing sessions keep their chosen profile; applications control their own ANSI colors. The baseline cursor blinking setting is retained. Nerd prompt symbols rely on Fontconfig fallback if Share Tech Mono lacks the glyph. Shell startup/prompt files are untouched. |
| Other terminals | `terminal/kitty-stark-os.conf` is an optional include with the same ANSI palette and canonical font. | Kitty was not installed during this audit, so this file is not applied. Browser/IDE terminals and other emulators have independent profiles. |

GTK documents its named-theme lookup under the user's XDG data theme directory
in [Gtk.CssProvider](https://docs.gtk.org/gtk4/class.CssProvider.html). Libadwaita
owns its own stylesheet and offers supported dark/light, contrast and accent
preferences; its [appearance documentation](https://gnome.pages.gitlab.gnome.org/libadwaita/doc/main/styles-and-appearance.html)
defines those boundaries. Do not use `GTK_THEME` globally or force a replacement
user CSS provider into libadwaita.

KDE's [GTK bridge implementation](https://github.com/KDE/kde-gtk-config/blob/master/kded/gtkconfig.cpp)
provides `setGtkTheme` separately from its preview method and synchronizes GTK
transports. Its [GTK2 editor](https://github.com/KDE/kde-gtk-config/blob/master/kded/config_editor/gtk2.cpp)
uses `GTK2_RC_FILES` when set; writing only `~/.gtkrc-2.0` can leave the effective
selection unchanged. `gtk-integration.json` snapshots the touched files and
GSettings user values, including the difference between an unset preference
and an explicit value. Restore changes only owned settings when unrelated
content has subsequently changed.

## Readability and native behavior

Primary text stays `#d9f4ff`; secondary and disabled widget text uses `#7fa6b8`
instead of the very faint decorative line color. Keyboard focus is explicitly
outlined in cyan. Selection uses `#12546a` with `#d8f8ff` text. Warning/error/
success colors remain amber/red/green and the associated icon shapes remain
different. There are no animated cursor frames, forced uppercase body text,
letter spacing changes that truncate native labels, or glow on text. Native
widget semantics, keyboard navigation and accessibility roles are retained by
importing the toolkit's own widget base before the theme overrides.

No PAM, polkit, keyring, password manager, browser authentication, credential
form logic or security prompt is replaced. Such dialogs can inherit native
palette/font settings where their toolkit allows it; their contents, ownership,
authentication mechanism and security boundaries remain native.

## Headless verification completed

- Regeneration to an empty temporary directory was byte-identical.
- `verify_app_extras.py` discovers all generated SVG icons dynamically, parses
  their XML, checks unique IDs and requires scalable viewBoxes.
- GTK 3.24 and GTK 4.22 native CSS parsers accepted the complete stylesheets
  with zero CSS parsing errors. Loading toolkit base CSS without a display
  emits expected icon-theme lookup criticals; this is parser verification,
  not a live rendering or accessibility audit.
- libXcursor loaded all 14 cursor files at each of four sizes (56 successful
  native decoder checks). A decoded contact sheet was visually checked.
- `verify_gtk_integration.py` passed in an isolated XDG directory with the native
  GSettings keyfile backend: repeated apply/restore, default versus explicit
  values, preserved unrelated options/CSS, effective legacy GTK2 path and
  rejection of paths outside the configured home.
- No visible app launch, KCalc test window, KWin restart, shell configuration
  change or live setting mutation was performed by this generator/audit.

Repeat the native checks with `/usr/bin/python3 desktop/verify_app_extras.py`.
The verifier removes `DISPLAY`, `WAYLAND_DISPLAY` and
`DBUS_SESSION_BUS_ADDRESS` before doing any native toolkit work. GTK versions
run in separate processes. The Xcursor checks also verify exact sizes, valid
hotspots, static frames, transparent backgrounds and premultiplied pixels.
GTK2 RC syntax is generated and reviewed but has not been exercised in a
native GTK2 application. These checks do not establish visual correctness for
every application, or replace a screen-reader/user accessibility review.

Native QFont decoding checks verify the actual family, size and weight of all
six KDE font assignments and the main Konsole profile. Ten-field serialized
font strings use Qt's legacy weight values (`57` Medium, `63` DemiBold, `50`
Normal). Putting modern `500/600/400` weights into that legacy format decodes
as Black; a textual family/size check would miss that readability defect.

## Read-only installed audit, 1 October 2026

The initial narrow check confirmed GTK3/4 settings.ini and installed theme
assets, but a deeper transport audit found stale Adwaita, font and icon settings
in the effective legacy GTK2 file, XSettings and GSettings. Earlier user CSS
also overrode the named theme. Native font decoding exposed the legacy weight
serialization defect above. The new transport integration and stronger native
verification address these gaps. All inherited Breeze, Breeze-dark, hicolor
and Breeze cursor themes were present; no duplicate Canonical Konsole profile
was installed.

`verify_app_extras.py --installed` now checks effective transport selections,
fallback GTK2 selection when that file is active, decoded font weights, baseline Konsole
assets/default and fallback theme availability. Run it after the final
installer pass, and repeat it after any further asset generation. This audit
cannot prove that already-running clients refreshed their cached icons,
cursors or GTK CSS.

KDE may regenerate the inactive plain `~/.gtkrc-2.0`; this machine uses
`~/.gtkrc-2.0-kde4` through `GTK2_RC_FILES`, so verification checks that active
file. A plain fallback block is installed/required only when it is the active
GTK2 configuration. Sandbox rollback tests cover both arrangements.

## Platform and app controlled surfaces

Flatpak/Snap runtimes may not expose host theme files; host styling does not
grant broad sandbox filesystem permissions. Web content, canvas/WebGL UI,
Electron/Chromium custom chrome, browser internal pages and remote desktops
have their own theme mechanisms. UEFI, bootloader, early boot, firmware,
hardware security prompts and privileged login services are outside this
per-user application theme. Accessibility high contrast preferences and apps
that explicitly opt out of system themes take precedence. These are honest
coverage boundaries, not reasons to imitate secure UI or inject blanket CSS.
