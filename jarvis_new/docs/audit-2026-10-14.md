# Jarvis reliability audit and practical development roadmap

Audit date: 14 October 2026. This report describes the current working tree,
including existing uncommitted work. It is not a claim that every integration
has been exercised against its live service or physical hardware.

## Calendar: a confirmed live blocker

**Follow-up, 14 October at 20:52 Singapore:** the user reconnected Google.
A fresh token refresh and read-only Calendar query succeeded. The original
authorization blocker below is resolved. Live event creation has not yet been
exercised.

A read-only authorization check against the personal Google connection failed
at token refresh with HTTP 400 and OAuth `invalid_grant`. The saved connection
includes `calendar.events`; this is not simply a missing calendar permission.
The machine timezone is `Asia/Singapore`. Recent Jarvis logs also contain
temporary DNS resolution failures and refused-access errors.

Reconnect the existing personal account using the repository's identity-checking
OAuth flow, from `jarvis_new`:

```bash
uv run python scripts/google_auth.py --account personal
```

The user must complete Google sign-in/consent. A successful reconnect still needs
a read-back check and a deliberately chosen event creation/read-back trial before
live calendar additions can be called verified. This audit did not create events
in the user's calendar.

If authorization repeatedly expires after about a week, inspect the Google Cloud
OAuth consent screen's publishing status. Google documents a seven-day refresh
token lifetime for external apps in Testing when requesting scopes beyond basic
identity. This is a possible explanation to investigate, not a verified finding
about this project's console configuration. See
[Google's refresh-token expiration rules](https://developers.google.com/identity/protocols/oauth2#expiration).

## Phone calling: confirmed listener failure and repair

The phone's Tailscale peer was online, but the native JarvisLink incoming-call
listener's server heartbeat was approximately 5.7 days old. The server correctly
suppressed invitations to that stale listener. Tailscale connectivity alone does
not start the app's incoming-call service. The last reported ringer mode was
vibrate; full-screen notification permission was false.

The native Android boot receiver previously restored the incoming monitor only
when microphone/hotword startup was enabled. The service also returned
`START_NOT_STICKY`, so Android would not request restoration after process
reclamation. Both paths are repaired, with the persisted incoming-call opt-in
checked on restoration. Status reporting now distinguishes clock skew, school
quiet hours and an active call from a healthy monitoring state.

The updated native APK is `phone/app/build/outputs/apk/debug/app-debug.apk`.
It compiled successfully, but no handset is connected through ADB, so it has
not been installed or tested for a real ring. Install it, then open native
**JarvisLink → Voice → Receive Jarvis calls**. If already enabled, toggle it
off and on. Keep Tailscale connected and verify the incoming-monitor notification
is present. Use normal ringer mode if an audible ring is wanted. This native app
is separate from the Flutter client, which does not implement inbound ringing.

## Implemented: explicit reminders and scheduled calls

The main voice assistant now exposes `schedule_task` and `scheduled_tasks`.
Examples of supported requests:

- “Remind me in 20 minutes to study chemistry.”
- “Remind me tomorrow at 9 am to pack my charger.”
- “Call me at 8 pm about revision.”
- “What reminders and calls are scheduled?”
- “Cancel that reminder.” Jarvis resolves the task ID, clarifying if needed.

The SQLite schedule survives process restarts. A separate bridge worker checks
due tasks even when passive proactivity is disabled. Default timezone is
`Asia/Singapore`; explicit offsets are accepted. Invalid times, past dates,
ambiguous/nonexistent daylight-saving times and missing content are rejected.
Concurrent workers and repeated calls within the same identified request do not
dispatch the same stored occurrence twice. A committed dispatch without a final
receipt becomes `uncertain` and is not replayed automatically.

Reminders use the existing desktop speech/notification transport, with a queued
announcement fallback. They are not phone push alarms. The computer and bridge
must be running at the due time; pending tasks over 60 seconds overdue become
`missed`. Native phone calls require enabled incoming calls, a listener heartbeat
under 60 seconds old, no competing invitation, and no guest or school quiet mode.
The existing school window is Monday–Friday 08:00–15:30 Singapore time; requests
for calls in that window are rejected at creation. Explicit calls bypass the
unsolicited-call category switches and daily budget. Offline/blocked calls are
recorded and not replayed later. Invitations expire after at most 45 seconds.

Statuses distinguish `pending`, `queued`, `notified`, `invited`, `blocked`,
`missed`, `failed`, `cancelled` and `uncertain`. A notification receipt does not
prove the user heard it, and an invitation does not prove the call was answered.
Guest mode blocks scheduling and personal reminder delivery.

Load these changes by restarting the bridge and voice agent through the usual
Jarvis launcher. `JARVIS_SCHEDULED_TASKS=0` disables the worker and rejects new
schedules. `JARVIS_TZ` controls scheduling timezone. This release implements
one-shot schedules; recurring schedules, phone-local alarms while the computer
is asleep, and spoken rescheduling are follow-up work.

## Confirmed bugs addressed

The audit added failing regression cases before implementing these fixes.

| Area | Defect and change |
| --- | --- |
| Calendar event bodies | Late-night default durations were truncated to 23:59, and overnight events could end before they began. Date arithmetic now handles midnight rollover. Invalid dates/times are rejected instead of becoming all-day events or raw date exceptions. |
| Calendar creation results | A response without a server event ID could count as a successful creation. Creation now requires the ID and checks known saved write scopes before requesting a token. |
| Calendar imports | Imports ignored the configured calendar/account and discarded failed items after partial success. The import flow now targets the configured destination and retains failures. |
| Background jobs | Jobs with the same kind and millisecond timestamp overwrote each other's record. IDs now include a random suffix while retaining the readable kind/time prefix. |
| Memory capture | A failed daily-note write still advanced the capture watermark and reported success. Failed writes now leave the conversation eligible for retry. |
| Forget/archive | Preferences could be removed even when archival failed, or reported removed when rewriting the preference file failed. Removal is conditioned on successful archival, and reported success follows the rewrite. |
| Proactive delivery | Failed output was marked delivered, permanently suppressing the same signal. Failed output now remains retryable on subsequent polls while its source still offers it; only successful speech consumes the speech counter. This does not add a durable queue for vanished source signals. |
| Mobile voice | A delayed mute response from an old call changed the state/error of a newer call. Responses now check call generation and transport identity. |
| Mobile chat | Replies completing after controller disposal notified a disposed notifier. Completion paths now honor disposal. |
| Mail history | Malformed timestamps could escape a supposedly nonthrowing logger or break history reads. Invalid records are skipped, timestamp zero is preserved, and nonpositive limits return no rows. |
| Voice startup | Native Piper cleanup was registered after feature-handler setup, so an early startup exception could retain the voice model. Cleanup is now registered immediately after session construction. |
| Tool lifecycle | A failed admission step could leave tool latency/busy tracking incremented and request scopes unclosed. Acquired scopes now unwind together and tracking begins only after admission succeeds. |
| Local speech recognition | Greedy `small.en` decoding invented extra words in a numeric request. Beam size 5 fixes the reproduced fixture and passes the ten-fixture comparison; other models retain their decoding settings. |
| Production frontend build | Two pre-existing formatting failures blocked the production build. Targeted formatting fixes preserve behavior and let the static export complete. |
| Incoming phone calls | Native monitor failed to restore independently of mic/hotword settings and after process reclamation. Boot and sticky-service restoration now honor persisted incoming-call opt-in. |
| Timed requests | There was no general durable voice scheduler. Reminders and explicit calls now have persistent one-shot schedules, cancellation, deduplication and truthful delivery receipts. |

The `small.en` experiment used the same ten cached, synthetic Piper audio
fixtures on CPU int8. Mean normalized word error rate was 0.0714 with beam 1
and 0.0 with beam 5; median decode time was 1.207 s and 1.275 s respectively.
This is one ordered comparison, not an acoustic field trial or a general model
accuracy claim. The unchanged default remains `base.en`. The benchmark cache
check now checks the actual English-only model selected by the application.
The decoding option is documented in the upstream
[faster-whisper project](https://github.com/SYSTRAN/faster-whisper).

Several existing tests also needed current-contract fixtures: typed verified
receipts instead of old response wording, a real volume readback mock, and
explicitly mocked WhatsApp page presence. Event-monitor host tests now disable
optional live model calls so unit tests do not depend on account credentials or
remote model output. These corrections preserve production verification checks.

## Authorized live restart and call check

On 14 October at approximately 20:52 Singapore, the user authorized restart and
confirmed Google reconnection. The Jarvis launcher was inactive; restarting its
existing user service brought up the shell, LiveKit server, registered voice
worker, wake listener and bridge. The bridge answered health checks, the wake
listener answered with its microphone unmuted, and the live bridge process has
the new `scheduled-tasks` thread. Google Calendar's read-only query succeeded.

The user then explicitly requested a test call. The scheduler created
`sched-800a479d22d54953` and the live worker issued one invitation. The phone was
connected with a fresh heartbeat, enabled notifications and a high-importance
call channel, but reported no full-screen permission and vibrate mode. It returned
`notification_failed`; the invitation expired unanswered. The user confirmed that
no incoming call appeared. This verifies scheduling and transport admission,
but does not verify notification presentation or call audio.

Review found that the incoming notification uses `CallStyle` while its ID is
different from the foreground monitor's ID. When full-screen access is absent,
it therefore has neither its own foreground-service association nor a full-screen
intent. Android's framework rejects this combination. That matches the live
symptom, though the exact handset exception is unavailable without ADB. See the
[Android notification service source](https://android.googlesource.com/platform/frameworks/base/+/android-13.0.0_r83/services/core/java/com/android/server/notification/NotificationManagerService.java).

The follow-up fix builds a normal high-priority category-call notification with
explicit Answer/Decline actions when full-screen access is unavailable. If an
allowed call-style notification is nevertheless rejected, it retries once using
that normal layout. Ringtone playback starts only after a successful post, and
the existing invitation/handled-ID guards prevent repeated ringing. Local error
logging records a fixed error category rather than exception text.

JarvisLink **3.6.1 (version code 19)** contains this fix. Android unit results:
318 cases, zero failures/errors, 14 skipped. The rebuilt debug APK is at the
same path above. It still requires handset installation, followed by another
user-authorized call and audio check. The computer services are already running
the updated backend; another backend restart is not required for this APK fix.

## What already exists

This is substantially beyond a chatbot scaffold. Current source includes a
realtime voice pipeline and alternative local components; specialist routing;
persisted background tasks; typed action outcomes; desktop and browser tools;
foreground OCR; personal memory and open threads; calendar, mail and job signals;
phone control; and a native HUD. The robotics arm is explicitly a mock, not
commissioned physical manipulation. Some planning documents lag the code.

The biggest improvements will come from making these parts cooperate reliably,
remember accurately, react quickly, and report real outcomes.

## Prioritized, implementable roadmap

Effort estimates below are planning estimates for one experienced developer,
excluding account setup, hardware acquisition and prolonged real-world testing.
Acceptance targets are proposed targets, not measured current performance.

### 1. Calendar as a dependable everyday tool — 2–4 days

Finish the reconnect and controlled live event check first. Add a dedicated
spoken single-event preparation tool alongside the existing import/email/exam
paths: resolve an exact date, time, timezone, duration and destination; read back
ambiguous details; create through `google_api.calendar_create`; return the server
event ID and link. Add explicit reschedule/cancel operations with event selection.

Hooks: `src/system/workspace_tools.py`, `src/google_api.py`, `src/prompts.py`.
Use TDD for tool/routing changes as required by `AGENTS.md`.

Done when: a corpus of everyday requests, overnight events, all-day ranges,
wrong-account cases, expired authorization, ambiguous dates and repeated attempts
produces the expected calendar state with accurate spoken results.

### 2. Measure and improve conversational response time — 2–4 days

Record monotonic timings for speech end, transcript finalization, routing,
first audible response, action dispatch and verified completion. Use 40 repeated
daily commands and 10 interruption cases. Measure cold and warm sessions
separately, and identify the slow stage before changing models or adding caches.

Hooks: `src/latency.py`, `src/agent.py`, `src/wake_client.py`,
`scripts/voice_runtime_benchmark.py`, `scripts/summarize_voice_latency.py`.

Done when: a report gives median/p95, failure rate and recovery time per route.
Aim initially for a short acknowledgement within one second and interruption
stopping output within 300 ms, then measure feasibility on the actual hardware.
Existing synthetic timing benchmarks do not establish physical speaker latency.

### 3. Give every promise a persistent operation — 4–7 days

Join background tasks, jobs, cancellation and action verification through one
operation ID. Store accepted/running/blocked/succeeded/failed/cancelled/unknown
states, evidence, next step and originating request. A restart should preserve
unfinished work and explain what can safely resume.

Hooks: `src/agent_tasks.py`, `src/jobs.py`, `src/action_outcome.py`,
`src/cancellation_control.py`, `src/system/background.py`.

Done when: “research this, draft a report, tell me when finished” survives a
restart; “how is that going?” refers to the same operation; “stop” ends its owned
work; a dispatched click alone never becomes a completed task.

### 4. Make personal memory correctable and attributable — 4–7 days

Add source/session/date, explicit versus inferred origin, confidence, expiry and
supersession to memory records. Begin with SQLite full-text retrieval and a
paraphrase evaluation set before choosing a vector service. Refresh relevant
memory at turn boundaries. Keep an editable view of remembered preferences.

Hooks: `src/memory.py`, `src/system/memory_tools.py`, `src/second_brain.py`.

Done when: 30 paraphrased personal-history questions retrieve supporting
evidence; a corrected preference supersedes the old one; forgotten information
does not reappear in retrieval; uncertain recall is identified as uncertain.

### 5. Maintain a small, fresh picture of the current situation — 3–5 days

Combine the active app/project, last authorized operation, upcoming deadline,
device state and relevant memory into a bounded context packet. Give every
observation a timestamp and expiry; missing information stays explicitly unknown.

Hooks: `src/context/telemetry.py`, `src/context/injector.py`,
`src/active_window.py`, `src/agent.py`.

Done when: switching projects invalidates stale assumptions, “continue that”
resolves only an unambiguous recent task, and window titles are not treated as
evidence of unseen screen content.

### 6. Make visual assistance verify its own results — 4–8 days

Connect existing OCR and computer-use observations to operation records. Keep
observations, hypotheses, attempted actions and verified results distinct. Ask
for a fresh observation after navigation, window changes or stale evidence.

Hooks: `src/screen_understanding.py`, `src/system/computer_use.py`,
`src/system/computer_freshness.py`, `src/system/action_verify.py`.

Done when: tasks involving loading screens, changed windows, missing buttons,
stale screenshots and user interruptions report accurate results and stop cleanly.

### 7. Deliver useful proactive help — 4–7 days

Extend signals with evidence, a proposed next action, expiry and relation to an
active goal. Add a durable bounded queue and delivery receipts for notifications
that need to survive outages. Offer accept/dismiss/snooze feedback, and group
related messages instead of repeating reminders.

Hooks: `src/proactive/engine.py`, `src/proactive/signals.py`,
`src/proactive/sources/`, `src/notify.py`.

Done when: failed delivery retries without double-delivery, dismissed suggestions
stay dismissed, focus time suppresses routine interruptions, and an unrelated
voice turn does not count as accepting every recent suggestion.

### 8. Tune personality through examples and evaluations — 3–5 days

Keep the conversational persona short: composed, concise, mildly dry humor when
appropriate, and specific about what happened. Move domain rules and aliases out
of the main prompt into tested routing and specialist policies. Evaluate ordinary
conversation, corrections, failures and urgent situations separately.

Hooks: `src/prompts.py`, `src/intent/`, `tests/test_persona.py`,
`tests/test_routing_dryrun.py`.

Done when: a scored conversation corpus shows the right tool selection and
appropriate brevity without repetitive honorifics, unnecessary sarcasm or invented
completion claims. Tune an available voice through listening tests; changing the
voice alone will not create the movie character's competence.

### 9. Make phone/desktop continuity explicit — 3–6 days

Carry the current operation, conversation summary and output-device ownership
between devices. A handoff should release old audio/output ownership and preserve
the task context, including after a reconnect.

Hooks: `src/phone_session.py`, `src/phone_calls.py`, `src/feature_sessions.py`,
`jarvis_mobile/lib/core/voice_ctrl.dart`.

Done when: starting on desktop and continuing on phone retains the same task;
only the chosen device speaks; reconnecting does not replay an already executed
command; late responses cannot alter replacement sessions.

### 10. Make the HUD show operational truth — 2–4 days

Use existing typed outcomes and job state to show what Jarvis is doing, what
evidence is current, what is waiting and which integration is disconnected. Make
simulated suit readings visibly distinguishable from actual measurements. Give
calendar reconnect and task recovery a clear route from the HUD.

Hooks: `src/action_outcome.py`, `src/health_recorder.py`,
`src/hud_events.py`, `frontend/components/`.

Done when: “listening”, “thinking”, “working”, “blocked” and “finished” reflect
actual lifecycle transitions, with no success animation for a failed operation.

### 11. Run repeatable live acceptance rehearsals — 2–3 days initially

Create ten routine demonstrations: wake/interrupt; open an app and verify;
create/read back a calendar event; resume yesterday's work; explain an error;
research and draft; announce a finished build; recover a disconnected call;
cancel running work; and handle unavailable hardware.

Done when: each release has observed outcome and latency evidence, kept separate
from unit-test totals. Start with a small dependable feature set and grow it.

### 12. Extend into the room and physical devices only after reliability — weeks+

Start with one feedback-capable device adapter or simulator task. Define actual
state feedback, offline behavior, bounded actions and a stop mechanism before
adding more hardware. The existing arm mock needs a real adapter, calibration
and hardware commissioning; it does not establish physical capability.

Hooks: `src/robotics/arm.py`, `docs/robot-arm-software.md`,
`docs/robot-arm-hardware.md`.

Done when: a narrow task succeeds repeatedly with observed state feedback and
fails predictably on sensor loss or interruption. General autonomous engineering,
unrestricted robotics and movie holograms are not short software upgrades.

## Suggested order

### Scheduling and phone follow-up — 3–5 days after handset verification

Build on the new one-shot scheduler with recurring rules and one record per
occurrence, an explicit reschedule operation, and a HUD list of upcoming tasks
and delivery receipts. Expose incoming-listener heartbeat age, notification
readiness and school-hour suppression in one device-status panel. Test Android
restart/reboot recovery and answering on Wi-Fi and cellular through Tailscale.
For reminders while the computer sleeps, add an explicit phone-local alarm
handoff with a device acknowledgement; a server-side SQLite timer alone cannot
deliver while its host is asleep.

Hooks: `src/scheduled_tasks.py`, `src/system/schedule_tools.py`,
`src/phone_calls.py`, `phone/app/src/main/java/dev/jarvis/link/svc/IncomingCalls.kt`.

Done when: each occurrence runs at most once, cancellation reaches the responsible
device, reminders survive the agreed offline cases, and the HUD clearly reports
which device has accepted responsibility for delivery.

### Implementation sequence

Start with calendar reconnection and reliability, then measured voice behavior,
operation continuity and memory. Add current-context grounding and verified
visual work next, then proactive goal support and cross-device continuity. Polish
voice and HUD alongside those measured improvements. Physical extensions come
after the software is dependable.
