# Event-monitor integration v3 (staged)

This revision adds useful bounded public-event tasks to the monitoring package, owner queries and explicitly granted local desktop alerts. It is separate from frozen v1/v2 and has not been applied or enabled. The overall `JARVIS_EVENT_MONITOR` flag remains default off; no monitor, model request or alert was created during validation.

## Owner interfaces and output grants

The actual Assistant exposes `monitor_create/list/status/stop` and protects them from adaptive demotion. Creation requires the current trusted `monitor {JSON definition}` command; stopping requires `stop monitor <exact-id>`. Body identity is never authority. The exact create fields are source, event, filters, expires (UTC epoch), outputs, session_scope, request_id, budget and ttl. Source/event/filter allowlists, finite expiry, quotas and replay checks remain.

Outputs are `status`, `session`, `activate`, and the new explicit `desktop-alert`. Desktop alerts require `session` plus `session_scope="desktop"`. Existing status/session/activate definitions acquire no popup permission. `activate` grants only a roomless text event agent. Private-owner session output is refused rather than silently mapped to desktop. Status-only definitions collect facts/counts; completed analytical summaries currently require session output and its prepared batches.

Authenticated bearer-token, loopback-only bridge routes are POST `/event-monitor/create`, `/list`, `/status`, `/stop`; GET `/event-monitor/list`, `/status?id=<id>` and `/session`. Status/list and session queries now include bounded recent completed summaries, model/fallback status and alert receipts. Summary replies omit large evidence bodies and report evidence count/IDs; full evidence is retained in the result store and accepted text inbox. No private conversation is exposed. Owner approval tickets are rechecked across disclosure; unknown screen-lock state refuses queries. An active authorized owner voice session can ask for status without granting background speech or a new call. Responses use no-store; errors contain fixed sanitized labels.

## Real task and durable result

The worker collects allowlisted public F1 facts, prepares immutable batches, processes up to ten pending tasks and then runs policy-controlled acceptance and alerts. Each task has one durable claim before a single bounded existing-client request to exactly `openrouter/free`, with an eight-second timeout. No environment fallback chain, tools, new credential or paid model is used. `JARVIS_MONITOR_SUMMARY` defaults on inside the otherwise disabled worker; set it to `0` for deterministic-only operation.

The free model chooses `summarize`, `compare_results`, or `ignore` and exact supplied evidence IDs through a strict JSON schema. Local code executes the selected task: renders factual race schedules/top results/historical replay summaries, or compares shared numeric driver positions for the same race in timestamp order. Model prose is not trusted or persisted. This is a bounded extractive/planning implementation, not open-ended analysis. Unknown tasks, invented IDs, extra fields, quota/backoff, resolver/provider failures and excessive input all produce a usable summary labeled `deterministic-fallback` with a fixed reason. Ignore suppresses that batch without an alert. Cancellation/expiry during inference discards the result. Shutdown prevents new task requests; an already running bounded request can finish without subsequent activation/alert.

Results and processing status persist in private `event_monitor/results.sqlite`. Full twenty-event facts are retained and dispatched as complete valid JSON with IDs, never a sliced JSON string marked delivered. Result stores cap at 5,000 and prune completed/discarded entries older than eight days. A crash leaving a processing claim waits fifteen seconds then uses `uncertain-previous-attempt` factual fallback without another model request. Optional original triage remains default off, shares the same model quota and now exposes its retained validated/unavailable/invalid status instead of losing it every pass. Triage and summary are separate phases; enabling both can use two requests per update.

## Acceptance, alerts and privacy

The installed SDK actually starts a roomless AgentSession/Agent with no LLM/STT/TTS/VAD/tools/MCP, recording, remote session host or audio/video streams. It is a bounded text projection of a completed result and full public evidence, not the summary processor itself. Durable text acceptance is distinct from provider success, task completion and notification transport. SDK projection failure preserves evidence for recovery. Start keys persist one identity/epoch/original five-minute deadline; retries cannot extend it. Context is capped at twenty events. Receipts and start maps cap at 5,000 with eight-day pruning.

A visible desktop alert uses the existing `notify-send` mechanism with fixed argv, sanitized bounded text, no shell, speech, queue, phone offer, room/wake dispatch or external message. It additionally requires the explicit desktop-alert output, active/unexpired monitor, fresh evidence, accepted batch, unlocked known screen, owner/non-guest/non-private state, no room/waking markers and existing quiet/DnD/focus/pause/budget policy. Unknown/held state refuses. Privacy/authority epoch is checked again immediately before transport; no critical override exists. The monitor SQLite lock serializes monitor stop against transport. Runtime alert claim, final guard, native transport and durable result settlement share the same lifecycle lock used by shutdown (lock order: monitor store, lifecycle, result store). Shutdown requests stop immediately, then drains that lock. If shutdown wins, transport is held; if transport is already in flight, shutdown cannot return until transport and its durable outcome settle. No submitted receipt can be created by a pending transport after shutdown returns. This proves local handoff ordering, not popup visibility.

Alert state is durably claimed before transport. `submitted` means notify-send returned zero, **not** that a popup was seen or a person received it. Nonzero is failed; timeout/crash is uncertain and is never automatically replayed. Held attempts can retry after policy permits. The parent must validate actual native visibility separately; desktop notification availability is assumed, not proven offline.

## Stop, shutdown and deployment

Monitor stop cancels the definition/outbox and retires all its accepted batch keys, including those appended to a session started by another monitor. Durable receipts associate every accepted key with its generation; the bounded live projection tracks every key actually projected and Store.batches maps keys to monitors. Retirement persists even when no generation is active, so a later restart cannot reintroduce stopped records. With other records present, the installed SDK context is replaced in place, preserving its instructions/config and the original identity/deadline while removing only stopped records. Other monitors remain active; no unrelated monitor definition, result or process is cancelled. If the projection becomes empty, its SDK session closes. If context replacement fails, that projection drains safely; unrelated definitions and historical results remain available for subsequent recovery. Historical receipts remain visible as past acceptance. Registry-driven cancellation is reconciled before each dispatch. Shutdown requests stop immediately and drains SDK state under the shared lifecycle lock; a close arriving after the worker's last check cannot start a late agent or accept evidence. A public fetch already in progress remains bounded and cannot be claimed settled until it returns. Close first drains any already in-flight fenced alert/receipt and SDK operation (transport timeout3seconds, each state DB busy timeout3seconds), then waits one second for its worker and returns false if still collecting; it retains singleton ownership until cleanup (worst-case collector about 160 seconds plus up to one in-flight summary request). No PID/process cancellation authority is added.

The bridge start/close hooks and singleton `event_monitor/worker.lock` are integrated. Existing owner-private home is required; symlink state/locks are refused. No service unit, flag, grant or credentials were changed. Apply only after independent review and exact baseline/dependency checks. Owned agent/bridge reload and actual activation require coordinated runtime gates; the previously observed live watch/call must not be disturbed. Live source/model/popup acceptance remains pending.

Rollback: disable any later enabled worker and wait for truthful settlement, verify candidate hashes, reverse the cumulative patch and preserve monitor/results/text-host/registry databases. Do not undo the deployed voice repair or clear profiles, permission state or unrelated services. Frozen v1 must not be applied on top of this cumulative revision.

## Verification and references

Test-only periodic asyncio wakeups address the sandbox loop limitation; production is unchanged. Tests cover the original four and two v2 independent review findings, blocked shutdown during transport through persisted outcome, both sides of a shared-session stop, real installed SDK context replacement, failure drain/restart exclusion, provider sanitization, full evidence, expiry/cancel during inference, grants, privacy/quiet, no replay after uncertain claims, owner summaries and existing voice transport/native-turn regressions.
